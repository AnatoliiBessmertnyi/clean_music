# Инструкции для агента

## Проект и источники информации

clean_music — Python CLI для обслуживания музыкальной коллекции.
Стек: Python >=3.13, Mutagen, pytest, Ruff, mypy.

- [README.md](README.md) описывает запуск и фактические ограничения.
- [docs/architecture.md](docs/architecture.md) разделяет реализованное,
  согласованные будущие решения и открытые вопросы.
- [docs/roadmap.md](docs/roadmap.md) задаёт приоритеты, последовательность развития
  и зависимости этапов; не заменяет scope и критерии отдельных Issues.
- `pyproject.toml` задаёт зависимости и настройки проверок; не дублируй их в документах.
- GitHub Issue — предпочтительный источник scope и критериев готовности отдельной
  задачи. До его оформления допустимо явно согласованное описание владельца.
- Перед работой изучи соответствующие код, тесты и требования. При противоречии
  между ними и согласованным решением сообщи владельцу до зависимых изменений.
- Сохраняй pipeline и принятый стиль. Изменяй архитектуру только по согласованному
  решению. Не добавляй абстракции, паттерны и зависимости без практической пользы.

## Общение, автономность и сессии

- Общайся по-русски, кратко и по существу. Не скрывай ошибки и ограничения проверок.
- После согласования выполняй задачу самостоятельно; не запрашивай повторное
  разрешение на уже согласованные действия. Вопросы нужны при существенной
  неоднозначности, выходе за scope или недостатке разрешений.
- Согласованные цели и ограничения могут разрешать исследование, локальные решения,
  правки документов и полный цикл Issue — ветка — коммиты — push — PR без отдельных
  подтверждений каждого шага. При изменении архитектурных принципов или существенном
  риске для пользовательских данных останови зависимую работу и объясни проблему.
- Одна задача — одна основная сессия. Переход к другой задаче или смена направления
  возможны только по прямому указанию владельца. Не начинай backlog самостоятельно
  и не выполняй несколько независимых задач разработки параллельно.
- Не завершай сессию только из-за продолжительности. При необходимости продолжения
  подготовь handoff: цель, Issue, scope, решения, изменения, проверки, ветка,
  состояние Git и следующие шаги. В новой сессии сверь их с репозиторием и Issue.
- Используй доступные средства оценки контекста честно; не выдавай предположение
  за результат `/status`. Не выполняй `/compact` без необходимости. Перед сжатием
  или сменой сессии сохрани краткую контрольную точку в чате; файл — только если
  это разрешено scope.
- Читай релевантные участки, ограничивай вывод и не повторяй проверки без причины.
  Не заявляй точный расход или остаток квоты без данных; о заведомо большом объёме
  обращений предупреди владельца.

## Аудит и проектирование

- По запросу владельца анализируй надёжность, безопасность, тесты, технический долг,
  производительность, архитектуру и пользовательский опыт.
- По умолчанию это read-only работа: не изменяй файлы, настройки и Git state,
  не создавай Issues, ветки, коммиты и PR без отдельного разрешения.
- Разделяй подтверждённые дефекты, риски и предложения. При необходимости предложи
  приоритетные направления развития, но не переходи к реализации автоматически.
- Результат — отчёт и передача владельцу для обсуждения. Создание PR не требуется.

## Согласование реализации

До изменений представь и согласуй план и scope: проблема и результат, решение,
компоненты, риски, необходимые архитектурные изменения, проверки, критерии готовности
и предполагаемый объём. Форма может быть краткой. Явно согласованное описание
владельца может служить таким планом; повторное согласование не требуется.

Внутри плана самостоятельно выбирай локальные решения, вспомогательные функции
и тесты. Небольшой связанный дефект исправляй только если это необходимо для задачи
и входит в scope. Не включай посторонние исправления и массовое форматирование.

Если они ещё не разрешены планом, предварительно согласовывай:

- изменение архитектуры, крупный рефакторинг, публичный API или CLI;
- поведение, затрагивающее пользовательские данные;
- новые зависимости или обновление версий;
- постоянные настройки разработки, CI и безопасности;
- расширение задачи и дополнительные внешние действия.

При существенном изменении плана останови зависимую работу и согласуй корректировку.
Не меняй настройки безопасности и разрешений Codex самостоятельно.

## Рабочий цикл реализации

1. Проверь ветку, рабочее дерево и remotes до исследования и повторно перед изменениями.
2. Изучи требования и согласуй план по правилам выше.
3. После согласования создай подходящий Issue, если его нет, и отдельную ветку
   `feature/<имя>` или `fix/<имя>`, если владелец не задал другой порядок.
4. Реализуй согласованный scope, выполни предкоммитную последовательность из раздела
   «Среда, проверки и CI», проверь diff и состав staged-файлов.
5. Создай коммит, отправь рабочую ветку и открой один PR по задаче.
6. Передай результат владельцу: изменения, проверки, ограничения и ссылка на PR.

Одна задача — один рабочий цикл и один PR, если явно не согласован иной порядок.
Проверку и merge выполняет владелец; ожидание merge не входит в работу агента.
При разрешённом порядке без PR завершением служат согласованный результат,
проверки и итоговый отчёт. После передачи результата не начинай следующую задачу
без указания владельца.

## Безопасность данных и инструментов

- Никогда не запускай обработку реальной музыкальной коллекции, даже с `--dry-run`.
  Для файловых проверок используй только синтетические данные, тестовые фикстуры
  и временные каталоги. Перед незнакомыми тестами проверь пути и побочные эффекты.
- Не удаляй и не перезаписывай пользовательские данные без отдельного явного
  разрешения. Правила будущего приложения о карантине не разрешают агенту
  обрабатывать реальную коллекцию.
- Не публикуй секреты, токены, ключи и содержимое файлов с секретами.
  Не отправляй пользовательские файлы во внешние сервисы без разрешения.
- Не устанавливай и не подключай инструменты ради их наличия. Новые MCP, Skills
  и интеграции предварительно согласовывай, объяснив пользу, риски и альтернативы.
  Применимые Skills используй согласно правилам среды, в пределах разрешений задачи.
- Не используй субагентов без отдельного разрешения.
- Не отправляй сообщения, комментарии и другие дополнительные обращения людям
  через внешние инструменты без явного разрешения. Issue и PR разрешены только
  в рамках согласованного рабочего цикла или отдельного указания.
- При недостатке прав используй штатный механизм запроса разрешения; иначе сообщи
  владельцу. Не обходи ограничения и не расширяй права самостоятельно.
- Системные инструкции и разрешения среды имеют приоритет; при конфликте сообщи
  владельцу.

## Git и коммиты

- Сохраняй незакоммиченные изменения пользователя. Изменения, существовавшие
  до задачи, нельзя включать в её коммиты без отдельного разрешения.
- Не изменяй `main` напрямую, не выполняй push в `main` и не делай merge.
  Явное разрешение владельца на локальное редактирование без ветки и коммита —
  исключение только для указанных файлов и действий.
- Не выполняй `reset --hard`, `clean`, принудительный push, удаление веток или
  переписывание опубликованной истории без отдельного согласования.
- Не меняй постоянные настройки Git и не используй команды, способные уничтожить
  или перезаписать незакоммиченные изменения.
- Добавляй только файлы и фрагменты текущей задачи; проверяй staged diff до коммита.
- Заголовок коммита: `<эмодзи> <тип>: <конкретное описание на русском>`.
  Он должен быть кратким и отражать основную суть изменения.
  Типы: ✨ feat, 🐛 fix, ♻️ refactor, 🎯 style, 📝 docs, 🧪 test, 🔧 chore, 👷 ci.
- Тело коммита необязательно для небольших изменений. Если оно нужно, используй
  столько предложений, сколько необходимо для понятного объяснения смысла и причины
  изменения, без жёсткого ограничения их количества. Желательно переносить строки
  тела примерно на 72 символах. Не превращай тело в подробный перечень файлов
  и не делай сообщение излишне многословным.
- Один коммит — одна логически связанная группа изменений.
  Не выдавай незавершённую работу за готовую;
  WIP-коммиты — только по явной договорённости.

## Среда, проверки и CI

Основная рабочая среда — Windows. Основной контур проверок проекта — локальный WSL
с отдельным окружением Python: pytest, Ruff и mypy. Linux-проверки выполняются в WSL.
Явные ограничения текущей задачи важнее обычного порядка: при запрете WSL его
не запускай, не подменяй результат Windows-проверкой и сообщи об ограничении.

Команды из корня проекта в его активированном окружении:

```bash
python -m ruff check .
python -m ruff format --check .
python -m pytest tests/ -v
python -m mypy .
```

Перед коммитом:

1. Составь явный список Python-файлов, изменённых в текущей согласованной задаче.
   Сверяй его с исходным Git status; одного `git diff --name-only` недостаточно.
   Файлы с ранее существовавшими незакоммиченными изменениями исключи целиком,
   если владелец отдельно не разрешил их обработку. При пустом списке пропусти
   изменяющие команды: запуск Ruff без путей может охватить весь проект.
2. Просмотри предлагаемые исправления командой
   `python -m ruff check --diff --no-unsafe-fixes <явный список файлов>`.
   Если исправление меняет поведение или требует неоднозначного решения, сообщи
   владельцу и не применяй его автоматически. Метка safe у Ruff не заменяет ревью.
3. Примени согласованные исправления:
   `python -m ruff check --fix --no-unsafe-fixes <явный список файлов>`.
   При необходимости ограничь набор исправлений, оставив спорные диагностики
   для отдельного решения; не отключай правила ради успешной проверки.
4. Выполни `python -m ruff format <тот же явный список файлов>` и просмотри diff.
5. Выполни проверки Ruff (lint и format --check), pytest и mypy командами выше.
   Ненулевой статус исправления из-за оставшихся диагностик не означает, что файлы
   не изменились: проверь diff и всё равно выполни остальные проверки.

Это порядок работы агента, а не установленный Git hook. Глобальные изменяющие
команды `ruff format .` и `ruff check --fix .` запрещены без отдельного согласования.
Разовое разрешение на обработку всех Python-файлов не меняет этот порядок для
следующих задач. Проверки без исправления могут охватывать весь проект.

- Восстановление окружения с объявленными зависимостями допустимо, если включено
  в план или отдельно разрешено. Не меняй декларации и файлы фиксации версий.
- Подбирай проверки по поведению и рискам; для исправления добавляй регрессионный
  тест, когда применимо. Не создавай формальные тесты, повторяющие реализацию.
- Во время разработки используй точечные тесты, перед PR — согласованный набор.
  Для документации выбирай релевантные проверки; запуск приложения не требуется.
- Не запускай автоматическое исправление и форматирование вне согласованной области.
- Различай новые и прежние ошибки. Посторонние дефекты фиксируй в отчёте,
  но не исправляй без согласования. Не заявляй успех незапущенных проверок.
- GitHub Actions не обязательны. Не создавай, не запускай и не меняй CI без
  отдельного решения владельца, включая действия, запускающие существующий workflow.
  Не предлагай Docker или возврат к CI без отдельного обсуждения.
- Планируемый локальный CI — один проверочный запуск в WSL без изменения исходников.
  Он не заменяет отдельный этап автоисправления и форматирования разрешённых файлов.
  Его реализация ведётся по [Issue #3](https://github.com/AnatoliiBessmertnyi/clean_music/issues/3);
  наличие задачи не разрешает начинать её без согласованного scope.

## GitHub Issues и Pull Requests

- Issue отражает согласованный scope, ожидаемое поведение, ограничения и критерии
  готовности. Не создавай посторонние Issues и не изменяй чужие Issues.
- Если GitHub или необходимые права недоступны, сообщи владельцу; не обходи ограничения.
- Заголовок и описание PR пиши по-русски: проблема, результат, проверки,
  существенные ограничения и связь с Issue. Не дублируй архитектурный документ.
- Не закрывай и не изменяй существующие Issues и PR за пределами согласованного
  scope. Создание Issue не завершает сессию: продолжай разрешённую реализацию.
