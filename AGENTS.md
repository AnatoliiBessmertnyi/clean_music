# Инструкции для агента

## Проект

clean_music — Python CLI для очистки музыкальных тегов, переименования файлов, нормализации исполнителей и объединения дубликатов.

Стек: Python >=3.13, pytest, Ruff, mypy.

Сохраняй существующую конвейерную архитектуру и принятый стиль кода.

Не усложняй архитектуру без необходимости. Не добавляй паттерны проектирования, абстракции и зависимости только ради их использования.

Принимай решения с учётом назначения проекта, существующей структуры и удобства дальнейшей поддержки.

## Общение и автономность

- Общайся на русском языке, кратко и по существу.
- Минимизируй вводные, повторы, пересказ запроса и очевидные объяснения.
- После согласования выполняй работу самостоятельно в пределах задачи.
- Не запрашивай повторное согласование уже разрешённых действий.
- Задавай вопросы только при существенной неоднозначности, необходимости расширить scope или получить разрешение.
- Экономь токены: читай релевантные файлы, ограничивай вывод команд, не повторяй проверки без причины.
- Краткость не должна скрывать ошибки, риски и ограничения проверки.
- Обязательные сообщения о ходе работы делай краткими и содержательными.
- Не запускай несколько независимых задач разработки параллельно.
- Не начинай самостоятельно реализацию задач из backlog.
- Итог: что изменено, что проверено, какие проблемы остались, ссылка на PR при наличии.

## Планирование и согласование

### Источник требований

- GitHub Issue — предпочтительный источник требований и критериев готовности задачи.
- Перед реализацией изучи Issue, если он существует, связанные участки кода и существующие тесты.
- Если требования противоречат текущей архитектуре или поведению приложения, сообщи об этом до реализации.
- Если Issue отсутствует, предложи оформить задачу через Issue либо используй явно согласованное описание владельца.

### Планирование задачи

До внесения изменений представь план, содержащий:

1. Понимание проблемы и ожидаемый результат.
2. Предлагаемое решение.
3. Затрагиваемые файлы и компоненты.
4. Возможные побочные эффекты и риски.
5. Необходимые изменения архитектуры, если они требуются.
6. План тестирования и проверки.
7. Критерии готовности.
8. Предполагаемый объём работ.

Дождись явного согласования плана. Оно разрешает перечисленные в плане этапы и действия; повторное согласование требуется при выходе за его границы. Если действие требует отдельного явного разрешения, оно должно быть прямо указано в согласованном плане либо согласовано отдельно.

### Границы самостоятельности

Агент может самостоятельно:

- выбирать локальные способы реализации согласованной задачи;
- определять необходимые вспомогательные функции и методы;
- исправлять небольшие связанные дефекты, включая ранее существовавшие, только если это необходимо для решения задачи и входит в согласованный план;
- добавлять тесты для проверяемого поведения;
- принимать небольшие технические решения в рамках существующей архитектуры.

Предварительного согласования требуют:

- изменение архитектуры приложения;
- крупные рефакторинги;
- добавление новых зависимостей и обновление версий существующих;
- изменение публичного API и пользовательского интерфейса CLI;
- изменение поведения, которое может повлиять на пользовательские данные;
- расширение scope задачи;
- изменения постоянных настроек разработки и безопасности.

### Техническое развитие проекта

Периодически по запросу владельца проводи технический аудит проекта.

Предлагай:

- устранение технического долга;
- повышение надёжности и безопасности;
- улучшение тестового покрытия;
- оптимизацию производительности;
- улучшение архитектуры;
- новые полезные функции;
- улучшение пользовательского опыта.

Оформляй предложения в виде приоритизированного backlog.

Не приступай к реализации этих предложений без отдельного согласования.

## Рабочий процесс

1. Получи задачу и её требования.
2. Исследуй соответствующие участки проекта без изменений.
3. Представь план и дождись согласования.
4. Проверь текущую ветку и состояние рабочего дерева.
5. После согласования реализации создай отдельную ветку:
   - `feature/<краткое-имя>`;
   - `fix/<краткое-имя>`.
6. Реализуй задачу в рамках согласованного плана.
7. Выполни необходимые проверки.
8. Проверь diff и состав изменений.
9. Сделай коммит, отправь рабочую ветку и создай Pull Request.
10. Предоставь владельцу итог для ревью.

Одна задача — один рабочий цикл и один PR, если владелец явно не согласовал другой порядок.

Задача завершена со стороны агента после выполнения согласованного объёма работ, проверок, создания PR и передачи итогового отчёта владельцу. Ожидание merge не входит в работу агента. При явно согласованном порядке без PR критерием завершения служат согласованный результат, проверки и итоговый отчёт.

Не начинай следующую задачу, пока текущая не завершена и не передана владельцу на проверку.

Не изменяй файлы и настройки до согласования плана или отдельного разрешения владельца на конкретные изменения.

Небольшие технические решения в рамках плана принимай самостоятельно.

При существенном изменении плана останови зависимую работу и согласуй корректировку.

Не включай в задачу посторонние исправления и массовое форматирование.

## Безопасность данных

Приложение работает с пользовательскими музыкальными файлами.

Поэтому:

- Никогда не запускай обработку реальной музыкальной коллекции, включая режим `--dry-run`.
- Для проверок используй только тестовые фикстуры и временные каталоги.
- Перед запуском незнакомых тестов проверь пути и побочные эффекты.
- Не удаляй и не перезаписывай пользовательские данные без отдельного явного разрешения.
- Не публикуй секреты, токены, ключи и содержимое файлов с секретами.
- Не отправляй содержимое пользовательских файлов во внешние сервисы без разрешения.
- Не изменяй настройки безопасности и разрешений Codex самостоятельно.
- При недостатке разрешений используй штатный механизм запроса разрешения Codex, если он доступен; иначе сообщи владельцу. Не обходи ограничения и не расширяй права самостоятельно.

## Терминал и Git

- Перед изменениями проверяй текущую ветку и состояние рабочего дерева.
- Сохраняй незакоммиченные изменения пользователя.
- Не изменяй `main` напрямую, не выполняй push в `main` и не делай merge.
- Не выполняй `reset --hard`, `clean`, принудительный push, удаление веток и переписывание опубликованной истории без отдельного согласования.
- Не изменяй постоянные настройки Git без согласования.
- При ошибках разрешений не расширяй права автоматически.
- Проверяй diff и состав staged-файлов перед коммитом.
- Добавляй в коммит только изменения текущей задачи.
- Не используй команды, которые могут уничтожить или перезаписать незакоммиченные изменения пользователя.

## Коммиты

Формат заголовка:

`<эмодзи> <тип>: <краткое описание на русском>`

Типы и рекомендуемые эмодзи:

- ✨ feat: новая функциональность
- 🐛 fix: исправление ошибки
- ♻️ refactor: изменение структуры без изменения поведения
- 🎯 style: форматирование и стиль без изменения поведения
- 📝 docs: документация
- 🧪 test: тесты
- 🔧 chore: обслуживание и инструменты разработки
- 👷 ci: автоматические проверки

Правила:

- Описывай конкретное изменение.
- Один коммит — одна логически связанная группа изменений.
- При необходимости добавляй пояснение причин в тело коммита.
- Не выдавай незавершённую работу за готовую.
- WIP-коммиты создавай только по явной договорённости.

## Проверки

Используй окружение проекта. Восстановление окружения с уже объявленными зависимостями допускается, если оно включено в согласованный план или отдельно разрешено владельцем. Добавление зависимостей и обновление их версий требуют предварительного согласования; не меняй декларации и файлы фиксации версий при восстановлении окружения.

Базовые команды:

    python -m pytest tests/ -v
    python -m ruff check .
    python -m ruff format --check .
    python -m mypy .

Правила:

- Подбирай тесты по изменённому поведению и рискам.
- Для исправления ошибки добавляй регрессионный тест, когда применимо.
- Не создавай формальные тесты, повторяющие реализацию.
- Перед PR выполняй согласованный набор проверок.
- Не запускай автоматическое исправление или форматирование вне согласованной области.
- Различай новые ошибки и ранее существовавшие.
- Не заявляй об успешной проверке, если она не запускалась.
- Ранее существовавшие ошибки, исправление которых не необходимо для текущей задачи или не входит в согласованный план, зафиксируй отдельно и не исправляй без согласования.

## GitHub Issues и Pull Requests

- После согласования плана самостоятельно создай GitHub Issue, если подходящего открытого Issue ещё нет. Это уточняет порядок оформления задачи из раздела «Источник требований»: до согласования можно использовать описание владельца, после согласования — оформить Issue.
- Issue должен отражать согласованный scope, ожидаемое поведение, критерии готовности и ограничения.
- Создание Issue в рамках согласованной задачи разрешено без дополнительного подтверждения.
- Не создавай посторонние Issues и не изменяй чужие Issues.
- После создания Issue продолжай выполнение задачи в той же сессии Codex.
- Если GitHub недоступен или необходимых прав нет, сообщи владельцу. Не обходи ограничения.
- Если Issue существует, используй его как источник требований и критериев готовности; иначе используй явно согласованное описание владельца.
- Уточняй противоречия между Issue, кодом и согласованным планом.
- После реализации и проверок создай коммит, отправь рабочую ветку и открой PR в рамках согласованной задачи, если владелец явно не согласовал другой порядок.
- Создание PR входит в согласованный рабочий цикл; дополнительные сообщения и комментарии другим людям через внешние инструменты требуют явного разрешения.
- Заголовок и описание PR пиши на русском.
- В PR укажи проблему, результат, проверки и существенные ограничения.
- Связывай PR с соответствующим Issue, если он существует.
- Проверку и merge выполняет владелец проекта.

## Управление сессиями и контекстом

- Одна основная сессия Codex предназначена для одной задачи.
- Не начинай другую задачу в уже используемой сессии.
- Не завершай сессию только из-за её продолжительности, если контекста достаточно.
- Используй `/status` для оценки состояния контекста, если команда доступна в текущем интерфейсе. Если она недоступна агенту, сообщи об этом владельцу; не выдавай оценку за результат выполнения команды.
- Не выполняй `/compact` без необходимости.
- Если контекст существенно заполнен, а впереди ещё большой объём работы, сначала сохрани контрольную точку, затем при необходимости используй `/compact`, если команда доступна. Контрольная точка — краткий handoff в чате; запись в файл допускается только в пределах согласованных разрешений.
- Если требуется новая сессия, сначала подготовь краткий handoff: цель задачи, ссылка на Issue, согласованный scope, принятые решения, выполненные изменения, затронутые файлы, результаты проверок, текущая ветка, состояние Git и следующие шаги.
- Перед продолжением в новой сессии обязательно сверь фактическое состояние репозитория и Issue. Не полагайся исключительно на handoff. Если Issue отсутствует или недоступен, явно укажи это.
- После создания PR и итогового отчёта задача считается завершённой. Следующую задачу начинай в новой сессии. Согласованный порядок завершения без PR из раздела «Рабочий процесс» сохраняется.
- Не расходуй контекст на повторные полные аудиты проекта и повторное чтение уже исследованных участков без необходимости.

## CI и автоматизация

- Локальные pytest, Ruff и mypy — основной механизм проверки.
- GitHub Actions используй как дополнительную страховку на Pull Request.
- Предпочитай бесплатные GitHub-hosted runners для публичного репозитория.
- Не создавай лишние CI-запуски без практической необходимости.
- Изменение CI-конфигурации предварительно согласовывай.

## MCP, Skills и дополнительные инструменты

- Не подключай инструменты только ради их наличия.
- Предлагай MCP-серверы, Skills и интеграции, только если они дают конкретную пользу проекту.
- Объясняй назначение инструмента, преимущества, риски и альтернативы.
- Установку и подключение новых инструментов согласовывай с владельцем.
- Не используй субагентов без отдельного разрешения.
- Не передавай внешним инструментам секреты; передачу содержимого пользовательских файлов допускай только с разрешения владельца.
- Применимые Skills используй согласно инструкциям среды; это не разрешает установку инструментов, изменение настроек или сетевые операции вопреки ограничениям владельца.
- Системные инструкции, правила безопасности и разрешения среды имеют приоритет над этим документом; при конфликте сообщи владельцу.

## Контроль ресурсов

- Учитывай ограниченный лимит ChatGPT Plus. Не заявляй точный остаток или расход квоты без доступных данных.
- Не используй чрезмерно длинный контекст без необходимости.
- Не перечитывай весь проект при каждой небольшой задаче.
- Не выполняй многократные одинаковые проверки без причины.
- Предпочитай точечные тесты во время разработки и полный согласованный набор перед PR.
- Не начинай самостоятельные задачи. В рамках согласованной задачи выполняй необходимые итерации исследования, реализации и проверки до достижения результата.
- Если задача требует большого количества обращений к модели, предупреди владельца о возможном расходе лимита.
