# Дорожная карта clean_music

## Статус и назначение

Это последовательность развития на основе аудита текущего кода и согласованных
принципов. Документ не утверждает ещё обсуждаемые алгоритмы и не разрешает
автоматически начинать следующие задачи. У каждого будущего Issue и PR будет
свой scope, проверки и критерии готовности.

Фактическая архитектура, принятые решения и открытые вопросы разделены в
[architecture.md](architecture.md); пользовательские ограничения — в
[README](../README.md), процесс разработки — в [AGENTS.md](../AGENTS.md).
Дорожная карта хранит последовательность и зависимости, Issues — спецификации
задач, PR — результат и проверки. Искусственные сроки не назначаются.

## Исходное состояние

Реализован семиэтапный интерактивный pipeline на Python/Mutagen для одной папки.
Текстовые преобразования вынесены в функции, зависимости этапам передаются явно.
Эту основу можно развивать без переписывания приложения.

Главный риск — безвозвратное удаление при конфликте имени или эвристическом
дублировании. Размер файла не доказывает качество; удаление уточнений может смешать
разные версии. Запись тегов выполняется на месте. Карантин, безопасная замена
и восстановление после прерывания отсутствуют.

Передаваемые пути могут устаревать, кэш привязан к пути, а dry-run смешивает
виртуальное состояние с реальной файловой системой. Ошибка чтения тегов неотличима
от их отсутствия; ручной ввод меняет регистр и не завершает заполнение тегов.
Есть 33 теста именования и парсинга, но нет достаточной проверки файловых отказов
и полного конвейера. Новые правила Ruff выявляют существующий технический долг;
его нельзя скрывать выключением правил или посторонними исправлениями.

Минимальный Python проекта — 3.13. Основная среда приложения — Windows 11/NTFS,
дополнительный сценарий — WSL2 с NTFS через `/mnt/d`. Основной контур локальных
проверок — WSL/Python 3.13. Версии, параметры инструментов и зависимости определяет
`pyproject.toml`; текущее ограничение упаковки и второй список зависимостей требуют
отдельного решения.

## Порядок и зависимости

Обязательная цепочка:

**1. Защитные ограничения → 2. Состояние и операции → 3. Карантин →
4. Безопасная запись тегов → 5. Полный dry-run → 6. Новая дедупликация.**

Карантин вводится раньше новой дедупликации: сначала нужна возможность безопасно
исключить и восстановить файл. Общая модель состояния предшествует обоим механизмам.
Dry-run развивается вместе с операциями на этапах 2–4; этап 5 закрывает весь pipeline.
Этап 6 использует его, а не создаёт отдельную логику удаления или симуляции.

Тесты добавляются в каждом PR; расширение покрытия не откладывается до последнего
этапа. Этапы 7 и 8 — улучшения, не блокирующие первые защитные изменения.
Их независимость не означает параллельную разработку без разрешения владельца.

Приоритеты: **P1** — сохранность данных и корректность; **P2** — сопровождение
и эксплуатация; **P3** — удобство инструментов. Номер этапа не равен номеру Issue.
Этап может потребовать нескольких небольших последовательных PR.

## Обязательные этапы

### 1. Немедленные защитные ограничения — P1

- **Цель:** прекратить неявную потерю данных до появления новой архитектуры.
- **Проблемы:** удаление при конфликте имени, старая дедупликация без карантина,
  удаление смысловых уточнений, массовое действие после ошибки ввода,
  небезопасное временное имя при смене регистра.
- **Результат:** конфликт сохраняет оба файла; прежнее исключение дубликатов
  временно отключено; содержательные теги сохраняются независимо от санитизации
  имени. Неподдержанное безопасное переименование пропускается с объяснением.
- **Зависимости:** нет; это первая рекомендуемая задача реализации.
- **Готовность:** проверены все вызываемые из CLI пути удаления и замены;
  регрессионные тесты покрывают разные размеры конфликтующих файлов, смену регистра
  имени и расширения, занятое временное имя, уточнения в тегах и неверный ввод.
  Тесты используют только временные каталоги и синтетические данные.
- **Риски:** временно уменьшится автоматизация. Запись тегов на месте и неполный
  dry-run ещё сохраняются; PR не должен объявлять приложение полностью безопасным.

### 2. Согласованное состояние и файловые операции — P1

- **Цель:** обеспечить одну актуальную картину файлов между этапами.
- **Проблемы:** устаревшие Path, повторные сканирования, кэш по старому пути,
  неявные результаты операций и смешение ошибок чтения с отсутствием тегов.
- **Результат:** постоянная идентичность файла, актуальные пути, явные результаты
  чтения и действий; изменения выполняются через единый исполнитель, кэш и контекст
  обновляются по подтверждённому результату. Сохраняется pipeline.
- **Зависимости:** этап 1. Конкретные типы и границы модулей уточняются в плане задачи.
- **Готовность:** интеграционные тесты показывают новые пути на следующем этапе,
  корректный кэш после действия и отказа, раздельные случаи неполных тегов и ошибок.
  Бесконфликтное и регистровое переименование проверены в Windows и WSL `/mnt/d`;
  существующие цели не перезаписываются. Логические переходы работают и в dry-run.
- **Риски:** смешение старого и нового состояния при миграции; различия семантики
  NTFS из Windows и WSL. Не вводить универсальную файловую систему ради переносимости.

### 3. Карантин и восстановление — P1

- **Цель:** дать обратимый механизм исключения копий до включения новой дедупликации.
- **Проблемы:** безвозвратное удаление, отсутствие происхождения файла и обработки
  прерванного перемещения.
- **Результат:** карантин вне сканируемой папки, запись исходного пути и причины,
  безопасное перемещение и восстановление без перезаписи. Автоочистки нет.
- **Зависимости:** этапы 1–2. Сначала согласовать границу поддержки другого тома;
  безопасный отказ допустим, скрытое копирование с удалением — нет.
- **Готовность:** тесты конфликтов карантина и восстановления, отказа перемещения,
  прерываний на границах операций и повторного восстановления. Неоднозначное
  состояние сохраняет все доступные данные и блокирует зависимое действие.
- **Риски:** частичный перенос и расхождение журнала с файлами. Безопасное применение
  не равно гарантии при отказе накопителя; поддерживаемые гарантии явно документируются.

### 4. Безопасная запись тегов — P1

- **Цель:** не изменять единственную доступную копию до проверки результата.
- **Проблемы:** запись Mutagen на месте, частичные сбои и отсутствие восстановления.
- **Результат:** временная рабочая копия, изменение и проверка, безопасная публикация.
  Оригинал доступен до подтверждённого завершения; постоянный архив всех оригиналов
  не создаётся. Используются уже введённые операции и механизм восстановления.
- **Зависимости:** этапы 2–3 и согласование конкретного аварийного протокола.
- **Готовность:** для MP3, M4A/MP4, FLAC, Vorbis и WMA проверены небольшие аудиофикстуры,
  ожидаемые и остальные поддерживаемые теги. Тесты покрывают прерывание после каждого
  значимого шага, ошибки копирования, публикации и очистки. После сбоя остаётся
  проверенный оригинал либо подтверждённый результат; неизвестные файлы не затираются.
  Отдельно установлена граница гарантий при потере питания в обеих целевых средах.
- **Риски:** нехватка места, блокировки, особенности форматов и атрибутов. Успешное
  чтение Mutagen не доказывает полную исправность аудиопотока.

### 5. Полноценный dry-run всего pipeline — P1

- **Цель:** получить последовательный прогноз тех же решений без файловых изменений.
- **Проблемы:** виртуальные пути проверяются на реальном диске, удалённые в модели
  файлы возвращаются после сканирования, расходятся переименования и статистика.
- **Результат:** единые решения и переходы состояния в реальном и сухом режимах;
  моделируются теги, имена и исключение из коллекции. Карантин, служебные файлы
  и журналы в dry-run не создаются.
- **Зависимости:** этапы 2–4; базовая симуляция должна появляться в них сразу.
- **Готовность:** на одинаковых временных фикстурах и ответах пользователя планы
  совпадают с успешным реальным выполнением; снимки дерева и байтов в dry-run
  неизменны, статистика различает план и факт. Пройдены сценарии полного pipeline.
- **Риски:** невозможно предсказать будущие блокировки и аппаратные ошибки;
  размер после виртуальной записи тегов нельзя использовать как известный факт.

### 6. Дедупликация и качество — P1

- **Цель:** оставить предпочтительную копию одной записи, сохранив самостоятельные версии.
- **Проблемы:** метаданные принимаются за доказательство, размер — за качество,
  разные записи могут автоматически объединяться после очистки названий.
- **Результат:** отдельно оцениваются кандидаты, совместимость версий, уверенность
  в совпадении и выборе копии. Высокоуверенные лишние копии автоматически уходят
  в карантин; неоднозначные группы требуют решения пользователя. Защищённые версии
  и принципы качества берутся из architecture.md, а не дублируются новой политикой.
- **Зависимости:** этапы 2–5. До реализации утвердить достаточные признаки уверенности
  и принятие остаточного риска; численные пороги и CBR/VBR-правила пока предварительны.
- **Готовность:** проверены разные форматы и длительности, CBR/VBR, недостаток данных,
  защищённые и неизвестные версии, Radio Edit/Album Version, противоречивые теги,
  разные записи с совпавшими признаками. Каждый исключаемый файл сравнивается
  с сохраняемым, без транзитивного объединения по цепочке похожести. Сбой или
  исчезновение победителя не разрешает дальнейшее исключение копий.
- **Риски:** ложные совпадения без анализа аудио, скрытое перекодирование и
  несопоставимость разных lossy-кодеков. Без объективного преимущества — ручной выбор.

## Улучшения после защитной основы

### 7. CLI, упаковка и технический долг — P2

- **Цель:** сделать эксплуатацию и сопровождение предсказуемыми.
- **Проблемы:** потеря регистра ввода, незаписанные теги после ручного ввода,
  неполная итоговая статистика, неполный пакет, расходящиеся источники зависимостей
  и накопленные диагностики новых правил Ruff.
- **Результат:** небольшие самостоятельные задачи исправления CLI, проверки установки
  вне исходного каталога и согласованного устранения lint-долга. Без автоматического
  ужесточения mypy, обновления зависимостей или массового рефакторинга.
- **Зависимости:** упаковка и lint-долг могут решаться отдельно; изменения ручного
  ввода и статистики должны учитывать модель этапа 2 и безопасную запись этапа 4.
- **Готовность:** проверки свободного ввода и ошибок, корректного отчёта, установки
  собранного пакета в изолированном окружении. Каждый PR имеет ограниченный diff;
  устранение диагностики не маскирует проблему изменением конфигурации.
- **Риски:** незаметное изменение CLI или музыкальных данных под видом рефакторинга;
  расширение scope из-за второстепенных улучшений.
- **Инфраструктурное исследование (P2):** [Issue #5 — Рассмотреть переход на uv
  для управления зависимостями и окружениями](https://github.com/AnatoliiBessmertnyi/clean_music/issues/5).
  Предполагаются единая конфигурация в `pyproject.toml`, общий `uv.lock` и независимые
  окружения Windows/WSL. Сначала исследуются сборка, dev-группа и безопасный переход;
  миграция не начата и требует отдельного согласования. Это улучшение не блокирует
  исправление проблем безопасности файловых операций на этапе 1.

### 8. Локальный CI-контур в WSL — P3

- **Цель:** один воспроизводимый запуск существующих проверок до коммита и PR.
- **Проблемы:** ручной запуск команд, пропущенные проверки, неверный Python или venv.
- **Результат:** минимальный проверочный сценарий, например `scripts/check.sh`;
  без GitHub Actions, автоисправления, установки пакетов и обработки коллекции.
- **Зависимости:** согласованный scope отдельной задачи; не блокирует этап 1.
  Существующие lint-ошибки должны давать честный ненулевой результат, а не мешать
  реализации самого сценария.
- **Готовность:** в WSL/Python 3.13 проверяются окружение, pytest, Ruff lint,
  Ruff format check и mypy; после проверки окружения выполняются все проверки
  независимо от результатов остальных. Есть сводка и корректный код завершения.
  Проверены отказы окружения, инструмента и проверки, пути с пробелами и запуск
  вне корня. Сценарий не изменяет исходники; автоисправление — отдельный этап.
- **Риски:** случайное использование системного Python, скрытая установка зависимостей,
  ошибочный успешный статус. Сейчас сценарий не реализован.
- **Задача:** [Issue #3 — Локальный CI-контур проверок в WSL](https://github.com/AnatoliiBessmertnyi/clean_music/issues/3).
  Она заменяет закрытые Issue #1 и PR #2 по GitHub Actions; PR #2 не слит.

## Проверка надёжности на всех этапах

Для файловых сценариев — только синтетические данные и временные каталоги.
Для Mutagen нужны небольшие аудиофикстуры разрешённого происхождения.
Чистые правила проверяются отдельно; файловые операции — на реальной временной
файловой системе и с управляемыми отказами; связность — полным pipeline.
Прерывание процесса проверяется отдельно от исключения Python, а устойчивость
к питанию не объявляется доказанной одними unit-тестами.

В каждом PR фиксируются реально выполненные pytest, Ruff и mypy, среда и ограничения.
Основной контур — локальный WSL; Windows/NTFS и WSL `/mnt/d` нужны для проверки
различий файловой семантики. Новые зависимости и дополнительные платформы требуют
отдельного обоснования. Нельзя объявлять успешными незапущенные проверки.

## Идеи за пределами текущего плана

Аудиоотпечатки, анализ сигнала, автоматическая очистка карантина по сроку,
рекурсивная обработка, сетевые файловые системы и расширенная поддержка платформ
не входят в обязательные этапы. Их польза и риски обсуждаются отдельно.
Возврат к GitHub Actions также требует нового решения, а не сохранения старого PR
ради уже выполненной работы.
