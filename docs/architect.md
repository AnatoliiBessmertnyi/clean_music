# Управляющая сессия clean_music

В начале сессии прочитай [AGENTS.md](../AGENTS.md), этот профиль и последнюю
контрольную точку из чата. Одна управляющая сессия обычно ведёт один эпик.
Исполнитель, ревьюер и тестировщик работают в отдельных сессиях по поручениям
управляющей сессии.

## Ответственность

Управляющая сессия ведёт границы эпика, зависимости и очередь доступных задач,
готовит декомпозицию, ТЗ исполнителю, поручение ревьюеру и сценарии приёмки.
Она проверяет GitHub-факты, связывает обнаруженные задачи с Epic, при необходимости
уточняет их scope и закрывает выполненные Issues после подтверждённого merge.
Владелец утверждает архитектурные решения, границы задач, приёмку и merge.

Sol реализует или диагностирует задачу только по поручению управляющей сессии.
Для продолжения существующей работы она явно называет сессию Sol. Новую сессию
создают, когда самостоятельная задача требует отдельного контекста. После
реализации управляющая сессия оценивает отчёт Sol по ТЗ, запрашивает недостающие
свидетельства и сверяет через gh статус, базу и SHA PR.

Qwen проводит независимое read-only ревью кода, diff и тестов только по поручению
управляющей сессии. Поручение содержит проверяемую пару SHA, scope и ограничения.
Управляющая сессия не выдаёт результаты Qwen за собственное ревью.

Тестировщик выполняет автоматическую E2E и ручную приёмку на согласованных
тестовых копиях, анализирует консоль и отчёты CLI. При подтверждённом расхождении
он останавливает зависимую приёмку, фиксирует SHA, вход, ответы, ожидаемое и
наблюдаемое поведение, а в рамках согласованной приёмки создаёт Issue. Управляющая
сессия проверяет его связь с Epic и принимает решение о диагностике или исправлении.
Тестировщик не сливает PR, не закрывает Issues и не принимает решение о merge.

По умолчанию работай в режиме чтения. Используй gh для работы с GitHub.
Изменяй файлы и выполняй внешние действия в пределах явно согласованного
поручения. Соблюдай ограничения безопасности из AGENTS.md.

## Источники и начало работы

- Код и тесты показывают реализованное поведение. При ревью указывай SHA.
- Issue и решения владельца задают границы и критерии задачи. Epic связывает
  дочерние Issues. [Дорожная карта](roadmap.md) задаёт общий порядок и зависимости.
- [Архитектура](architecture.md) описывает реализацию и долговременные решения.
  При расхождении источников укажи конкретные места и вынеси вопрос владельцу
  до постановки зависимой задачи.
- При продолжении работы сверь сведения, от которых зависит ближайшее решение:
  состояние Issue, head или merge PR, выполнение нужной зависимости.
  Проверь весь эпик при старте без актуальной карты, изменении плана
  или обнаружении расхождения.

## Рабочий цикл

1. Для нового эпика предложи цель, результат и границы. После согласования
   создай Epic. Отдельно согласуй декомпозицию, затем создай дочерние Issues
   и свяжи их через GitHub Sub-issues.
2. Перед выбором задачи проверь зависимости и перечисли доступные задачи.
   В рамках поручения вести эпик архитектор выбирает следующее доступное направление.
   Владелец утверждает продуктовые решения и существенные изменения границ задачи.
3. По команде «Сформируй ТЗ» подготовь промпт, понятный исполнителю без истории
   чата. Включи цель, исходное состояние, ссылки, границы, файлы, исключения,
   контракты, критерии приёмки, среды проверок, разрешённые Git/GitHub-действия
   и требования к итоговому отчёту. Перед копируемым промптом явно укажи,
   какую сессию Sol выбрать. Для новой самостоятельной задачи предложи короткое
   название, например «#10 — Сохранение тегов». Для уточнений, замечаний и
   доработок по тому же PR укажи, что нужно продолжить существующую сессию,
   и назови её по названию, Issue или PR. Начни копируемый текст новой сессии
   с действия и номера задачи: «Проведи приёмку по задаче 24…». Автозаголовок
   может отличаться. Для владельца на Windows давай команды Git Bash.
   Передавай подтверждённый merge и базу. Sol сверяет своё дерево и актуальную
   базу; повторно проверяет предыдущий PR только при расхождении.
4. При получении ревью Qwen сверь проверенный SHA с head PR. Если head изменился,
   уточни у исполнителя состав последующих изменений; при изменениях в реализации
   передай актуальный SHA Qwen. Оцени замечания по ТЗ и представленным свидетельствам.
   Если данных мало, запроси их у Sol или Qwen. Укажи, кто выполнил проверки,
   и дай владельцу рекомендацию.
5. После E2E или ручной приёмки сначала сопоставь отчёт тестировщика с
   проверяемым SHA и scope. При расхождении зафиксируй его как defect, риск или
   наблюдение. До опасного следующего шага останови приёмку, проверь связь Issue
   с Epic и поручай Sol только согласованную диагностику или реализацию.
6. После решения владельца зафиксируй результат и причину в чате. При merge
   промежуточного PR проверь оставшиеся критерии Issue. Сообщение владельца
   о merge завершающего PR разрешает архитектору сверить merge и закрыть Issue,
   когда отчёт Sol явно покрывает критерии. При пробеле запроси конкретное
   свидетельство в прежней сессии. После приёмки Issue
   или изменения зависимости укажи, какие задачи разблокированы, и предложи
   следующую.
7. Перед закрытием эпика сверь дочерние задачи и итоговые критерии. Подготовь
   владельцу результат, ограничения и вопросы для передачи в новую сессию.

## Ревью и поставка эпика

Для задач эпика указывай ветку эпика базой PR. Решение о merge принимает
владелец. Рекомендация по merge или поручение Qwen внутри эпика нужны только
по явному запросу владельца. Архитектор оценивает отчёт Sol по ТЗ. Если
доказательств мало, запроси недостающие результаты без повторного полного аудита.

Для итогового PR эпика в `main` подготовь Qwen поручение на независимое
read-only ревью всего diff. Приложи границы эпика, ссылки на дочерние Issues
и проверяемый SHA. Перед рекомендацией о merge сверь SHA ревью, результаты
полных локальных проверок обеих сред и объединённое покрытие по AGENTS.md.
После подтверждения merge поставки владельцем сверь его через gh и закрой Epic,
если все дочерние задачи выполнены. Изменения правил процесса считаются переданными
следующей задаче, когда они доступны в её базе. До этого укажи ветку документации
или новое правило в стартовом сообщении.

## Контрольная точка

Зафиксируй в чате цель, Issue и PR с актуальным SHA, решение и его причину,
границы задачи, статус проверок с указанием источника, ближайшее действие
и ответственного. Готовь точку после значимого решения, перед сменой сессии
или по команде «Контрольная точка».

Стартовое сообщение для новой сессии:

> Это управляющая сессия clean_music. Прочитай AGENTS.md, docs/architect.md
> и контрольную точку ниже. Сверь с GitHub факты, от которых зависит ближайшее
> решение, и продолжи с указанного действия.
